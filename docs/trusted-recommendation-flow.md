# 추천 순서·답변 위치·인접 지역 신뢰성 (2026-11-10)

## main에서 재현한 경로

조사 기준 main은 PR #13 병합 커밋 `feee7d9`이다. 새 세션의 기본 규칙 검색 자체는 슬로우조깅을 먼저 계산한다. 그러나 그것만으로 최종 화면 순서를 보장하지 못했다.

1. `app.send → handle_turn → extract_conditions → _search`에서 Gemini가 걷기를 파크골프로 잘못 추출하면, main은 그 활동으로 직접 검색한다. 모의 성공 응답을 주입해 main의 실제 결과가 파크골프가 되는 것을 재현했다. 이는 실제 배포 Gemini 응답을 확보했다는 뜻은 아니다.
2. main의 app.py는 `state.alternatives`를 받은 순서대로 렌더링한다. 파크골프가 먼저 들어간 이전 세션 후보를 주입해 main AppTest의 첫 실제 선택 버튼이 ‘파크골프 정보 보기 →’임을 확인했다. 점수와 렌더링 순서가 달라도 마지막 검증이 없었다.
3. 일반 아이디어도 별도 정렬 목록으로 함께 렌더링되어 공식 대안과 같은 활동이 중복될 수 있었다.
4. 인접 지역 검색이 0건이면 기존 results/references/alternatives를 비우지 않고 새 메시지만 갱신했다. 따라서 강서구 활동이 새 인접 지역 답변 아래 다시 표시되는 경로가 코드상 확인됐다.
5. 일반 답변 스크롤은 150/600ms 보정뿐이었으며 긴 상세 답변만 더 오래 보정했다. Streamlit의 실제 `.stMain` 요소는 `stAppScrollToBottomContainer`로 자동 하단 이동을 수행해 늦은 렌더링과 충돌할 수 있다.

실제 iPad 배포의 Gemini 원문·조건 상태·메모리 모듈 버전은 직접 확인하지 못했다. 위는 재현 가능한 코드 경로와 확인된 상태 재사용 문제이며, 배포에서 어느 경로가 발생했는지 하나로 확정하지 않는다.

## 하나의 실제 추천 흐름

`질문 → 의도/조건 추출 → 명시적 활동 고정 → 공식 JSON 후보 → 자격·지역·시간·예산 필터 → 공통 점수 → 중복 제거 → 최종 점수 재계산 → 같은 순서로 버튼 렌더링`

- `anchor_request`: ‘걷기’처럼 활동을 명확히 말하면 다른 활동으로 임의 치환하지 않는다. 다른 활동으로 추출된 태그/분류도 그대로 필터로 쓰지 않는다. 질문에 없는 시간·거주지·예산·대상/목적 등을 이번 발화의 새 조건으로 추가하지 않으며 이전 조건은 보존한다. 명시한 강서구를 다른 지역으로 치환하지 않는다. 실제 관심 태그는 명시된 것만 유지한다. 복수 활동이 명확하면 임의로 하나를 고르지 않는다.
- `programme_options / ordered_options`: 공식 ID로 원본 행을 다시 조회하고 기존 필터를 적용한다. 같은 활동은 선택 버튼 하나로 묶고 같은 프로그램 ID도 중복 제거한다.
- `score_program`: 검색과 화면이 공유하는 점수·분류·한 문장 이유를 만든다.
- `prepare_view`: 이전 세션의 순서/점수/이유를 신뢰하지 않고 다시 계산한다. 최신 표시 상태를 대화 상태에도 반영해 표시된 버튼과 선택 가능한 후보가 일치한다. 공식 대안이 있으면 별도의 일반 아이디어 목록을 나란히 중복 표시하지 않는다. 실제 자료가 없을 때 일반 아이디어는 유지한다.
- 기존 `related_options`, `adjacent_search`도 같은 파이프라인에 위임한다. Gemini 성공·키 누락·실패 경로가 같은 정렬을 사용하며, 실패 안내를 성공처럼 바꾸지 않는다.
- 적용 중인 지역·활동·시간·예산·나이·초보 조건을 짧게 표시한다. 예를 들어 오전 조건 때문에 저녁 슬로우조깅이 제외되면 무조건 다시 포함시키지 않는다. 알려진 양수 비용은 무료 조건에 맞지 않으며, 비용 null은 무료로 취급하지 않는다.

## 점수와 이유

점수 구성은 코드와 세션의 `score_parts`로 검사할 수 있다. 기본 대화 화면에 기술적 점수/진단은 노출하지 않는다.

| 항목 | 규칙 |
| --- | --- |
| 활동 관련성 | 직접 일치 300, 유사 활동 200, 다른 대안 100 |
| 목적 | 명시한 운동 목적과 공식 체육 분류가 맞으면 +10 |
| 움직임 | 일반 활동 방식이 보행/수중 동작 등으로 이어지면 +10 |
| 강도 선호 | ‘가볍게’가 명시됐고 속도 변화가 있는 방식이면 -5 주의 |
| 지역 | 요청 자치구와 같으면 +10, 동의한 인접 지역은 별도 범위 |
| 대상 | 기존 자격 검사 충족 +5, 추가 확인이 필요한 경우 +2; 부적합은 후보에서 제외 |
| 이동 선호 | 이동을 줄인다고 명시했을 때 도구/시설 확인 부담 -3 |
| 접수 상태 | 접수중 +3, 현장 참여 +2, 미확인/접수 전 +1, 마감/종료 0 |

나이로 건강·운동 능력을 추정하지 않는다. 강도/이동 항목은 일반 활동 방식의 비교이며 실제 강도·거리·접근성을 확인한 점수가 아니다. 실제 강도는 확인 필요라고 설명한다. 자격/시간/예산을 완화해 점수로 끼워 넣지 않는다. 부가 점수의 합이 활동 관련성 단계 차이 100을 뒤집지 않는다.

새 세션의 ‘강서구 걷기 프로그램 찾아줘’에서는 슬로우조깅 222점, 파크골프 118점이다(다른 명시 조건이 없을 때). 슬로우조깅 이유는 ‘걷기처럼 보행 중심인 유사 운동이지만 속도와 실제 강도는 확인해야 해요.’이며 접수 마감은 별도 표시한다. 파크골프는 다른 대안으로 표시한다. 접수 가능 여부가 관련성을 뒤집지 않는다.

## 인접 지역은 별도 검색 상태

동의 전에는 조회하지 않는다. 동의 후 `flow=adjacent`, `search_scope={kind, origin, allowed, covered}`로 분리하고 새 결과·대안·일반 아이디어·시설 목록을 모두 새로 구성한다. 현재 공식 10건에는 인접 지역 자료가 없으므로 다음처럼 안내한다.

> 현재 확인된 인접 지역 프로그램 자료가 없습니다.

강서구 추천은 새 결과로 복사하지 않는다. 이전 대화는 유지하고, 필요한 이름 목록은 접힌 ‘이전에 찾은 강서구 활동 · 새 인접 지역 결과 아님’ 안에서만 표시한다. ‘강서구 추천 다시 보기’를 눌러야 명시적으로 지역 검색을 되돌린다. 인접 범위에서 시간 조건을 바꾸면 그 별도 범위를 유지하며, 사용자가 강서구를 명시하면 지역 검색으로 돌아온다.

인접 지역 데이터가 있는 경우에만 지역을 명시한 카드를 공통 점수순으로 최대 3개 표시한다. 그룹 메타데이터도 실제 데이터가 있는 자치구만 포함한다. 마감/미확인 자료는 참고로 구분하고 신청 가능하다고 승격하지 않는다. 이 경로는 테스트 전용 양천/마포 레코드로 검사했으며 운영 JSON에는 가상 레코드를 넣지 않았다.

## 답변 시작 위치

`ui/reply_scroll.js`가 일반 답변과 상세 답변을 함께 다룬다. 질문 제출/음성 녹음 종료/선택 버튼 동작으로 생긴 새 답변의 시작 앵커를 기준으로, ResizeObserver·실제 스크롤 이벤트·짧은 재시도로 최대 3초 동안 레이아웃을 정렬한다. 중요한 첫 카드가 아니라 맨 마지막 위젯을 따라가지 않는다. 이전의 일반/상세별 별도 타이머 경로는 제거했다.

사용자가 스크롤하거나 다른 동작을 시작하면 강제 이동을 중단한다. 응답 대기 중 이전 대화를 읽으면 실제 스크롤 결과를 저장하고 새 답변이 나타날 때 그 위치를 보존한다. 새 메시지 렌더링 시작 후의 자동 하단 이동을 읽기 위치로 다시 저장하지 않는다. 가상 키보드 크기 변경도 고려하지만, 기록을 읽는 중에는 최신 답변으로 강제 이동하지 않는다. 수집하는 것은 UI 앵커 ID·개수·스크롤 수치뿐이며 질문/음성 내용을 기록하지 않는다.

Chromium의 320/390/768px과 응답 지연 중 위로 스크롤하는 경우를 검사했다. 실제 iPad/iPhone Safari·Android 기기, 주소창/키보드·관성 스크롤은 미검증이다. ResizeObserver가 없으면 타이머로 보완하며, Streamlit 내부 DOM/class에 의존하므로 업그레이드 시 재검사가 필요하다. 모든 Safari 버전이나 모든 지연에서 무조건 같은 위치라고 보장하지 않는다.

## 검증

- 전체 자동 테스트 **137개**: 기존 126개와 신규 11개. 잘못된 Gemini 활동 추출/실패 대체, 반대 순서·위조 점수의 이전 상태, 점수와 한 문장 이유, 동의/거절/0건/조건 유지, 인접 지역 그룹, 실제 AppTest 첫 버튼을 검사한다.
- Chromium **32개 흐름**: 기존 25개 + 새 질문의 실제 첫 버튼·답변/첫 카드/상세 위치·인접 결과 격리·이전 지역 복귀를 3개 너비×기본/잘못된 모의 Gemini 6개로 검사하고, 지연 응답 중 이전 기록 읽기 1개를 추가했다.
- 공식 10건과 구버전/None 포맷터, KeyError/ISO 재발 방지, 신청 안내, 기존 모의 STT/TTS/오류/지역 동의도 회귀 검사했다.
- 실제 Gemini/OpenAI API, 실제 Safari, Community Cloud 배포는 미검증이다. 모델·Secrets·공식 데이터·의존성·음성 모듈은 그대로다.

공식 인접 자료 조사와 제외 이유는 [조사 기록](adjacent-source-review.md)에 기록했다. 실시간 웹 검색을 앱에 추가하지 않았다.

배포 후에는 Community Cloud의 main/app.py를 확인하고 Reboot app과 브라우저 새로고침으로 서버/브라우저 코드 버전을 맞춘 뒤 실제 질문을 다시 검사한다. 실제 API 응답과 iPad 상태를 직접 확보하지 않은 한 배포 해결을 확정하지 않는다.

브라우저 테스트는 같은 질문을 반복해도 이전 문장을 새 응답으로 오인하지 않도록 새 답변 앵커 ID를 기다린다. 프로그램명·접수 상태를 추천 이유보다 먼저 보여 좁은 화면에서도 첫 실제 자료가 보이도록 했다.
